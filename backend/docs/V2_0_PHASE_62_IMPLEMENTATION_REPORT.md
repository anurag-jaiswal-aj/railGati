# RailGati V2.0 — Phase 62 Implementation Report

## Objective
Implement Train Route Structural Shortest-Path Divergence analytics to evaluate how much a train's actual consecutive route length diverges from the minimum structural bounds of the active snapshot network. The metric represents historical timetable-network structural shortest-path divergence.

## Strict Constraint Adherence

1. **₹0 Budget Constraint**
   - No external APIs or paid routing services were used.
   - No dedicated graph databases (like Neo4j) were introduced.
   - The solution strictly queries the local relational datastore.

2. **Historical Timetable Isolation**
   - The graph traversed is definitively constrained to edges explicitly belonging to the active snapshot (`timetable_snapshot_id`).
   - Structural edges are evaluated based on the active `TrainStopObservation` timeline, honoring `RailwayGraphBuild` constraints.

3. **Unreachable Semantics**
   - If no structural path exists connecting the Start terminal to the End terminal within the bounded depth, `shortest_structural_edges` correctly returns `null`.
   - `divergence_absolute` and `divergence_ratio` gracefully return `null` in unreachable scenarios.

## Topological Interpretation
The Breadth-First Search explicitly enforces an **undirected graph interpretation** as defined in the discovery. Although the timetable fundamentally originates as directed sequences ($A \rightarrow B$), the BFS evaluates neighborhood expansion symmetrically. An edge is traversed if `from_station_id` OR `to_station_id` connects to the current traversal frontier. This ensures consistency with the undirected neighborhood semantics established in Phase 60.

## Algorithm & Performance Audit
To evaluate the structural shortest path, we replaced the multi-query Python BFS with a native SQL recursive Common Table Expression (CTE).

We investigated three recursive CTE strategies:
1. **Recursive CTE with Array Accumulator**: Passing a `visited` array along the path. This fails spectacularly on cyclic railway graphs because standard SQL cannot share the `visited` array across divergent branches. Evaluating all possible simple paths triggers an exponential $O(D^N)$ Cartesian explosion.
2. **Recursive CTE without state deduplication (`UNION ALL`)**: Causes redundant branch expansion without bounding the exponential explosion.
3. **Recursive CTE with implicit state deduplication (`UNION`)**: **[Selected Strategy]**

**The SQL Formulation:**
```sql
WITH RECURSIVE search_graph(station_id, depth) AS (
    SELECT :start_id, 0
    UNION
    SELECT 
        CASE WHEN e.from_station_id = sg.station_id THEN e.to_station_id ELSE e.from_station_id END,
        sg.depth + 1
    FROM search_graph sg
    JOIN railway_network_edges e ON 
        (e.from_station_id = sg.station_id OR e.to_station_id = sg.station_id)
        AND e.timetable_snapshot_id = :snapshot_id
    WHERE sg.depth < :max_edges
)
SELECT depth FROM search_graph WHERE station_id = :end_id ORDER BY depth LIMIT 1;
```

**Why this avoids path enumeration (Deduplication Semantics):**
- The recursive relation contains only `(station_id, depth)`.
- The `UNION` operator strictly deduplicates identical `(station_id, depth)` states.
- This does **not** mean a station is expanded only once globally. A station can still appear at multiple depths (e.g., `(X, 2)` and `(X, 3)` are distinct rows).
- However, it safely prevents enumerating every possible *path string* to a station. Identical states at the *same* depth are collapsed.
- The search is explicitly bounded by `max_depth` (the train's actual consecutive edge count).
- The worst-case recursive state space is therefore safely bounded by $O(|V| \times \text{max\_depth})$, subject to the actual query planner's behavior.

### PostgreSQL `EXPLAIN ANALYZE` Findings (Train 15905)
- **Planning Time**: 0.381 ms
- **Execution Time**: 14189.296 ms (~14.1s)
- **Recursive CTE Rows**: `3,970,224` generated by the Union.
- **Recursive Iterations**: `loops=698`. The recursive nested loop executes strictly $L+1$ times where $L$ is `max_edges` (697).
- **Index Usage**: The `OR` join is highly optimized by PostgreSQL. It dynamically splits into a `BitmapOr` operation utilizing two distinct precise indexes: `Bitmap Index Scan on ix_network_edges_from_station` and `Bitmap Index Scan on ix_network_edges_to_station`. There are **no sequential scans** on the edges table.
- **Short-circuiting**: The `ORDER BY depth LIMIT 1` operation **does not** short-circuit the execution during the recursion phase. PostgreSQL evaluates the entire breadth-first frontier out to `max_edges` (697), accumulates all states, and then applies a `top-N heapsort` (Memory: 25kB; no disk spilling) to select the minimum.

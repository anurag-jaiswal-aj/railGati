# v2.0 Phase 6 Discovery: Network Corridor Analytics

## 1. Phase 6 Title
**Network Corridor Analytics (Continuous Service Route Discovery)**

## 2. Problem Statement
Phase 2C provides the shortest topological path between two stations via a Breadth-First Search on `RailwayNetworkEdge`. Phase 5 validates whether a *specific, provided* path is traversed by continuous historical services. However, users and analytical systems currently cannot ask the graph: *"What are the actual, utilized physical corridors (paths) between Station A and Station D, and which corridor carries the most continuous trains?"* Attempting to answer this by exhaustively traversing the `RailwayNetworkEdge` graph for all possible paths and testing each via Phase 5 would cause a Cartesian explosion and evaluate countless topologically valid but physically unutilized routes. 

## 3. Why It Follows Phase 5
Phase 5 established the rigid domain semantics for continuous single-train traversals across topological segments. Phase 6 inverts this paradigm: rather than checking a user-supplied path for continuous services, it aggregates the exact contiguous sequences of utilized train stops to *discover* the distinct topological paths (corridors) naturally formed by the historical dataset. It builds upon Phase 5's conceptual foundation of structural continuity while solving the unbounded graph-traversal problem using deterministic relational algebra.

## 4. Existing Capabilities Reused
- `TrainStopObservation` boundary checking (used in v1.x direct journeys).
- Phase 5 missing-data timing semantics (`_parse_time_to_minutes`).
- `DatasetSnapshot` isolation.
- Canonical station resolution and API validation patterns.

## 5. Candidate Directions Considered
- **Historical Timetable Journey Search (Passenger Transfer Routing):** *REJECTED.* Modeling 1-hop or 2-hop transfers between different trains requires explicit calendar operating days (e.g., "Runs on M,T,W"). The current Datameet-derived timetable provides `source_day_offset` (relative days) but lacks absolute calendar alignments. Joining Train 1 and Train 2 based purely on time-of-day offsets creates theoretically unsafe, passenger-invalid journeys. This violates the core domain boundaries.
- **Historical Service Journey Comparison:** *REJECTED.* v1.2 already provides direct journey comparison. Phase 6 must advance the v2.0 graph capabilities.
- **Connection-Risk Foundations:** *REJECTED.* Requires valid transfer semantics, which are rejected above.
- **Network Corridor Analytics (Selected):** *SELECTED.* Safely utilizes explicit, single-train continuous services to discover macroscopic network topology (corridors) without theoretical transfer risks.

## 6. Architectural Trade-offs
To discover all paths between A and D:
- **Option A: Recursive CTE on `RailwayNetworkEdge`.** Explores all topological paths, bounded by `max_hops`. *Trade-off:* Massive Cartesian explosion. Evaluates paths that no single train actually drives. 
- **Option B: Array Aggregation on `TrainStopObservation`.** Identify trains connecting A and D, extract their intervening station sequences using `array_agg(station_id ORDER BY stop_sequence)`, and group identical arrays into distinct corridors. *Trade-off:* Extremely fast, perfectly bounded to actual utilized routes, and requires zero recursive graph traversal. 
**Selection:** *Option B*. It leverages PostgreSQL's highly optimized array aggregations to natively discover graph routes.

## 7. Selected Scope
**Network Corridor Analytics.** Discovering and ranking the distinct topological routes (corridors) formed by continuous historical services between an origin and destination.

## 8. Explicit Scope
- Given an origin and destination station, return all unique topological station-paths (corridors) traversed by at least one continuous historical train.
- Aggregate the total number of continuous services operating on each corridor.
- Calculate the fastest observed historical duration across all services in each corridor.
- Maintain strict snapshot isolation.

## 9. Explicit Non-Scope
- **Passenger Routing / Transfers:** Will not combine different trains to form a corridor.
- **Calendar Validity:** Will not claim the corridor operates on a specific real-world date.
- **Live Operations:** No live delays or operational status.

## 10. Historical-Data Semantics
Corridors represent aggregated historical structural connectivity. A returned corridor proves that in the specified snapshot, train(s) physically drove that exact sequence of stations. It does not guarantee current passenger availability.

## 11. Domain Semantics
A **Corridor** is defined as a unique, ordered array of canonical station codes connecting an Origin to a Destination, historically generated by the contiguous stop sequences of one or more continuous train services.

## 12. Timing Semantics
- Uses the Phase 5 timing strategy.
- Analyzes `departure_time` at the origin and `arrival_time` at the destination for each service in the corridor, applying `source_day_offset`.
- Returns the `fastest_duration_minutes` observed within the group. Missing timing gracefully evaluates to `null` and is ignored in the `MIN()` aggregation.

## 13. Transfer Semantics
Explicitly N/A. The feature strictly utilizes continuous, single-seat historical services to avoid calendar-day fallacies.

## 14. Data / Query Model
**Tables:**
- `train_stop_observations` (for bounding O-D and extracting path sequences)
- `stations` (for resolving codes)

**Query Structure:**
1. **CTE 1 (Bounds):** Find `train_id`, `start_seq`, `end_seq` where `station = O` and `station = D` (`start_seq < end_seq`).
2. **CTE 2 (Path Extraction):** Join bounds back to `train_stop_observations` for stops between `start_seq` and `end_seq`. Use `array_agg(station_id ORDER BY stop_sequence)` to generate the path array.
3. **Outer Query (Aggregation):** `GROUP BY path_array`, calculating `COUNT(DISTINCT train_id)` and `MIN(duration)`.

**Cardinality:**
Highly bounded. The number of physical rail corridors between any two cities is naturally limited (typically < 10 distinct macroscopic routes).

## 15. Snapshot / Provenance Semantics
The entire query must be strictly filtered by a single `timetable_snapshot_id`. No cross-snapshot data is permitted.

## 16. Service-Layer Responsibilities
- Validate input (Origin != Destination).
- Resolve canonical station IDs.
- Execute the array-aggregation SQL query.
- Map returned arrays back to canonical station codes.
- Format the response and enforce deterministic ordering.

## 17. Proposed API
**Endpoint:** `GET /api/v1/network/corridors`
**Method:** GET

## 18. Request Parameters
| Name | Type | Location | Required | Default | Description |
|---|---|---|---|---|---|
| `origin` | `string` | Query | Yes | - | Canonical origin station code (e.g., `NDLS`) |
| `destination` | `string` | Query | Yes | - | Canonical destination station code (e.g., `BPL`) |

## 19. Response Shape
```json

  "origin": "NDLS",

  "timetable_snapshot_id": 2,
  "corridors": [
    {
      "path": ["NDLS", "AGC", "GWL", "VGLJ", "BPL"],
```

## 20. Validation Rules
- `origin` and `destination` must be provided and valid canonical codes.
- `origin` must not equal `destination` (case-insensitive).

## 21. Error Semantics
- **422 Unprocessable Entity:** Origin equals destination.
- **404 Not Found:** Origin or destination station unknown.
- **503 Service Unavailable:** Active snapshot unavailable.

## 22. Deterministic Ordering
1. `service_count` DESC
2. `fastest_duration_minutes` ASC NULLS LAST
3. Array Length (`json_array_length(path)`) ASC

## 23. Resource Limits
Output payload is naturally bounded by real-world physical routes. No arbitrary `LIMIT` is required, preventing pagination complexity. 

## 24. Performance Considerations
PostgreSQL `array_agg` with grouping is exceptionally performant. Because it anchors on O-D bounds using existing indices (`ix_train_stops_snapshot_station`), it completely circumvents the exponential time complexity of BFS graph traversal. 

## 25. Query Strategy
```sql
WITH bounds AS (
  SELECT o.train_id, o.stop_sequence as start_seq, d.stop_sequence as end_seq,
         o.departure_time, o.source_day as start_day,
         d.arrival_time, d.source_day as end_day
  FROM train_stop_observations o
  JOIN train_stop_observations d ON o.train_id = d.train_id AND o.snapshot_id = d.snapshot_id
  WHERE o.station_id = :origin AND d.station_id = :dest AND o.stop_sequence < d.stop_sequence
    AND o.snapshot_id = :snapshot
),
paths AS (
  SELECT b.train_id,
         array_agg(tso.station_id ORDER BY tso.stop_sequence) as path_array,
         -- (duration logic mapped to minutes here) as duration
  FROM bounds b
  JOIN train_stop_observations tso ON tso.train_id = b.train_id AND tso.snapshot_id = :snapshot
  WHERE tso.stop_sequence >= b.start_seq AND tso.stop_sequence <= b.end_seq
  GROUP BY b.train_id
)
SELECT path_array, COUNT(train_id) as service_count, MIN(duration) as fastest_duration_minutes
FROM paths
GROUP BY path_array
ORDER BY service_count DESC;
```

## 26. Index Strategy
The query leverages the highly selective composite index `ix_train_stops_snapshot_station` on `(snapshot_id, station_id)` to instantly identify `bounds`. A primary key lookup (`train_id`, `stop_sequence`) handles the sequence extraction. No new indexes are required.

## 27. Benchmark Methodology
- **A. Normal case:** Dense intercity corridor (e.g., Delhi to Kanpur).
- **B. Sparse case:** Cross-country corridor with few direct trains (e.g., Jammu to Kanyakumari).
- **C. High-Density Multi-Route case:** Stations connected by multiple differing physical paths (e.g., Delhi to Mumbai, which traverses Western Railway vs Central Railway).
- For each, record: `EXPLAIN ANALYZE` (Planning, Execution, Scans, Join Strategy, Array Aggregate cost) and application-level execution time.

## 28. Test Strategy
- **Normal case:** Valid O-D returning multiple distinct corridors.
- **Empty case:** Topologically reachable but no direct continuous services.
- **Unknown station:** Validates 404.
- **Same station:** `origin == destination` validates 422.
- **Timing edge cases:** Missing departure/arrival timings gracefully evaluate to `null` and do not break the `MIN()` aggregation.
- **Snapshot isolation:** Ensure corridors from old snapshots do not bleed in.
- **Deterministic ordering:** Assert `service_count` DESC sorting.
- **Regression:** Phase 3/4/5 tests must remain passing.

## 29. Security Considerations
ORM and parameterized text queries prevent SQL injection.

## 30. ₹0 Validation
Relies strictly on native PostgreSQL array aggregation and relational grouping. 

## 31. Future Extension Points
The discovered corridor arrays can be fed into a UI mapping layer to visualize the actual trunk routes of the Indian Railway network, grouped by volume, creating a powerful macroscopic intelligence tool.

## 32. Risks
- **Memory Consumption in Array Aggregation:** Very long trains (100+ stops) aggregated in memory across many trains could consume higher `work_mem`. However, PostgreSQL routinely handles integer arrays of length < 150 trivially within standard `work_mem` limits.

## 33. Unresolved Questions
- **RailwayNetworkEdge Validation:** Because the corridors are derived directly from actual `TrainStopObservation`s, they are implicitly topologically valid. It may be redundant to cross-validate the returned array against `RailwayNetworkEdge`, but this will be evaluated during implementation.
